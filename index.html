What it is, in one paragraph

The Climb is a web page that runs a small AI model on your own computer and shows it working a calculation it gets wrong at the first try. A checker that is not the model reads every line it writes. A step that is true is kept and crossed off the calculation. A step that is false is dropped, and split into smaller steps. What is left to do goes back to the model, so every pass starts from a smaller problem than the last, until the checker says the answer is right, or until it is clear this problem is beyond it. Both endings are shown.

A calculator gets these sums right at once. That is not the point. The point is the pattern: a small model that cannot do a job in one go, made to finish it by something outside it that can say "this step is right, that one is not". The same pattern fits any work where a step can be checked by code. Everything here was measured on tasks sealed before the run, the failures are kept, and you can run all of it again on your own machine.

What was measured: On 96 sealed problems, the model alone got 36.5% right at one try. Told only "not right" and given 8 tries, 44.8%. Left to re-read its own work, 29.2%. With every step checked, wrong steps split and kept steps remembered, 70.8%. 28 problems were never reached, and they are listed under the wall.

Start here

The words this page uses. A pass is one reply from the model, working the problem out line by line. The checker is code, not the model: it works each line out exactly, keeps the lines that are true and drops the ones that are false. The climb asks the model again with what was kept, pass after pass, until the answer is right or it stops. It is set against one try (a single reply), a retry (the same number of tries, told only "not right") and the naive loop (the model re-reads its own answer with nothing checking it). Before anything was measured, the problems were sorted into three kinds, as predictions: easy (expected right at the first try), climb (expected wrong at first, reachable with checked steps) and wall (expected out of reach); the page shows where the predictions were wrong. The wall is also the list of problems the climb did not reach: one stalled when the model gave the same reply to the same ruling, and one has nothing to climb by when no part of it can be checked on its own (finding the two primes behind a product gives no partial credit). The sealed run is the measurement, on problems the build was never tuned on, made after every file that could change a result was frozen. "Gated" in the blueprint means a mutation test changed that part's code many ways, one small change at a time, and its tests caught every one; an equivalent change makes no difference to what the code does, and its reason is written down in src/witness.baseline.json.

How it works

One pass has four steps. They repeat until the answer is right or the climb stops.

  1. Try. The model is asked to write its working one small step per line, as working = number, and to end with ANSWER: number. It is the only part that guesses.
  2. Check. The checker is code. It reads each line, works the left side out exactly with whole-number fractions, and compares. True: kept. False: dropped. It never says what the right number would have been. It rules on the final answer the same way. The checker also holds the calculation the problem asks for. Each true line that is a step of it is crossed off with the value the model wrote, and a false step is replaced by smaller steps made from its own numbers: 144 × 45 becomes 144 × 40 + 144 × 5. What remains is sent back as Left to do, so every pass starts from a smaller problem than the last. A true line that is no part of the calculation is not called right, and a smaller step that is dropped is split again.
  3. Remember. A kept step is written once into a memory with twelve chambers, placed by its digits so that steps about the same numbers sit together. Before the model is asked, the memory is asked for every step the problem has to do. A step it holds is crossed off there and then, and named to the model as already checked. Only checked steps ever go in.
  4. Reuse. A problem's passes are one growing conversation. The browser keeps what it computed for the earlier turns, so a later pass only reads the new part. The time this saves is measured on this page (step 7 of Start here), not assumed.

Why not just let the model re-read its own work? That is the "naive" loop in the results. Nothing outside the model tells it which line is wrong, so it can change a right answer into a wrong one as easily as the other way. The climb differs in one thing only: something that is not the model rules on every step.

Adoption: what this does for your business

Where it fits

Work with several steps where each step can be checked by code, and where a wrong result costs more than a slow one. Reconciling a ledger line by line. Filling a form whose fields must add up. Converting units through a chain. Generating code that has to pass tests. In each, the checking code already exists or is cheap to write. What this pattern adds is the loop around it: keep what passed, split what failed, try again from there.

Where it does not

Work with no checker. If nothing outside the model can say whether a step is right, there is nothing to keep and nothing to drop, and this page's own "naive" loop shows what is left. Judgement calls, open questions and anything creative are out. So are problems with no partial credit: see the wall.

Rolling it out

  1. Pick one multi-step job where you already have, or can write, a check for each step.
  2. Write that check as code. It must never be a model, and it must never hand the model the right value.
  3. Run the job one try only, on your own cases, and count how often it finishes. That is your baseline.
  4. Run it with the loop: check each step, keep, split, retry. Count again, and count the extra model calls.
  5. Keep the cases it never finishes. They tell you where a person, or a bigger model, is still needed.
For buyers: the case, without hedging

What it is

A measured demonstration that a small model on ordinary hardware can be made to finish multi-step work it fails at cold, when every step is checked by code. On the sealed problems it took the share finished from 36.5% at one try to 70.8%.

What it is not

It is not a calculator and it is not a general assistant. It does not make the model smarter. It makes the model's mistakes visible one step at a time and gives it another go at the wrong step only. It did not reach 28 of 96 problems.

Chief executive

The question to ask of any AI system is what happens when it is wrong. Here a wrong step is caught by code before it reaches an answer, and the system either gets there or says it did not. Both are counted on this page.

Finance

The price of the climb is model calls. The climb made 264 model calls on 96 problems, 2.75 per problem against 1 for a single try. On your own hardware those calls cost electricity, not tokens. The table below prices the same tokens at cloud rates so you can see what the loop would cost if you bought it by the token.

Operations

Every pass is recorded: what the model wrote, which lines were kept and dropped, what the checker said back. A problem that does not finish is handed to a person with that record, so they start from the kept steps and not from nothing.

Technology and security

No server, no account, no API key. The model and the checker run in the browser tab. While the sealed run was made, the browser counted 0 network requests. The model files come from the public WebLLM model library and are cached by the browser; their hashes are not pinned by this page, which is a limit stated here plainly.

Risks, answered straight

  • "It is only arithmetic." Yes. Arithmetic was chosen because the finish line cannot be argued with. The pattern carries to any job with a step checker, and nothing here measures such a job. That would be your test to run.
  • "The checker knows the answer, so it could just give it." It could. It does not: it says right or wrong for a line the model wrote, splits a wrong step, and shows what is left to do. Every value it crosses off is one the model wrote. You can read every message it sent in any recorded climb.
  • "The checker holds the calculation. Is that not most of the work?" It is real help, and it is the point. The checker knows what the problem asks for and keeps the books: what is done, what is left. The model still has to do every step. The retry loop is the same model with the same number of tries and none of that help, and the gap between the two is what the books are worth. For your own job this is the part you write: the steps the job needs, as code that can tell when each is done.
  • "More tries would have got there anyway." That is what the retry loop measures: the same number of tries, told only "not right". With the same number of tries and only "not right" to go on, the model finished 43 of 96; the climb finished 68. 26 problems only the climb reached, 1 only the retry loop reached (exact test p = 4.2e-7).
  • "It costs more compute." Yes. 2.75 model calls per problem against 1, and 2446 s of model time on the sealed set against 989 s.
  • "Some problems never finish." Yes. 28 of 96 sealed problems were not reached. They are listed under the wall.
  • "Not every laptop has WebGPU." Step 1 checks this. Without it the model cannot run here, but the published runs can still be re-judged here.

White paper: checked depth

The problem. A language model can be asked to look at its own answer and improve it. Left alone, this helps less than it sounds. The model has no way to know which part was wrong, so a second look is as likely to break a right step as to fix a wrong one, and by the fifth pass it is mostly reading its own mistakes back.

The idea. Put something outside the model that can rule on a step. Then each pass can stand on what the last pass got right. The steps that were checked are never in doubt again; only the wrong ones are worked again, in smaller pieces. Depth then adds up instead of washing out.

What this page tests. Whether that is true for a small model on real hardware, by how much, and at what cost. It runs the same problems four ways and reports all four. It also tests the stronger version of the idea, that each pass should shrink what is left as fast as squaring does, and reports whether it held.

What it does not show. That the model learned anything. The model at the last pass is the model at the first. What changed is what it was standing on.

The one rule. A number is on this page only because the checker or the clock measured it in a recorded run. Nothing here was written down first and hoped for. Where a prediction was wrong, the prediction and the measurement are both shown.
